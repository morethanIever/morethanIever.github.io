### 컴파일 기본 옵션

```bash
gcc -Wall -Wextra -o 프로그램이름 소스파일.c && ./프로그램이름
```

| 옵션 | 의미 |
|---|---|
| `-Wall -Wextra` | 흔한 실수를 경고로 알려줌 (W = warning) |
| `-o 이름` | 출력 파일 이름 지정. 없으면 `a.out` |
| `-g` | gdb 디버깅 정보 포함 (소스 줄 번호, 변수 이름) |
| `-O0` / `-O2` | 최적화 끔 / 켬 |

## 1. 개발환경과 첫 컴파일

### 1-1. hello.c

```c
#include <stdio.h>

int main(void) {
    printf("Hello, C!\n");
    return 0;
}
```

```bash
gcc hello.c            # 출력 이름을 안 주면 a.out
ls                      # a.out  hello.c
./a.out                 # → Hello, C!
gcc hello.c -o hello    # 이름 지정
./hello                 # → Hello, C!
```

- 출력 이름을 지정하지 않으면 `a.out`
- `gcc hello.c -o hello` : 출력 이름을 지정
- 소스를 고치면 다시 **컴파일** 필요
- `void` : 인자를 받지 않는다

### 1-2. main의 반환값

```c
#include <stdio.h>

int main(void) {
    printf("센서 초기화 실패\n");
    return 7;   // 0이 아니면 "비정상 종료"라는 약속
}
```

```bash
gcc -Wall -Wextra exitcode.c -o exitcode
./exitcode; echo "종료 코드: $?"    # → 종료 코드: 7
```

- **`$?`** : 직전 프로그램의 **종료 코드**
  - `main`의 반환값을 셸에서 `$?`로 읽을 수 있음, 0이 정상 종료
  - 셸 스크립트·Makefile·systemd가 이 값으로 성공/실패를 판단

### 1-3. 헤더 없이 컴파일

```c
int main(void) {
    printf("Hello\n");   // stdio.h 없음
    return 0;
}
```

```bash
gcc -Wall -Wextra nohdr.c -o nohdr
# → error: implicit declaration of function 'printf'
```

- 헤더 = "이런 함수가 있다"는 선언
- 헤더가 없으면 컴파일러가 `printf`의 인자·반환 타입을 검사할 수 없음 → `stdio.h` include 필요
- 이때 나는 에러: `implicit declaration`

## 2. 빌드 과정

### 2-1. 전처리 → 컴파일 → 어셈블 → 링크

```bash
gcc -E hello.c -o hello.i     # ① 전처리:  #include, #define을 풀어 씀
gcc -S hello.i -o hello.s     # ② 컴파일:  C → 어셈블리
gcc -c hello.s -o hello.o     # ③ 어셈블:  어셈블리 → 기계어 (오브젝트)
gcc hello.o -o hello          # ④ 링크:    오브젝트 + libc → 실행파일
ls hello*                     # hello  hello.c  hello.i  hello.o  hello.s
```

**① 전처리기** — `gcc -E hello.c -o hello.i`

- `#include`, `#define` 처리
- `int printf(char*, …);`처럼, 전처리를 통해 헤더를 읽어 `printf`가 처리됨
  - 헤더를 include하지 않으면 `error: implicit declaration of function 'printf'`
- `hello.i` — 전처리 결과, `stdio.h`가 통째로 펼쳐짐

```c
# 1 "hello.c"
# 1 "/usr/include/stdio.h" 1
typedef struct _IO_FILE FILE;
extern int printf (const char *__restrict __format, ...);
... (약 800줄 생략)
# 2 "hello.c" 2

int main(void) {
    printf("Hello, C!\n");
    return 0;
}
```

**② 컴파일** — `gcc -S hello.i -o hello.s`

- C → 어셈블리
- `hello.s` — 어셈블리 (x86-64, `-O0`)

```nasm
        .section .rodata
.LC0:   .string "Hello, C!"
        .text
        .globl  main
main:
        pushq   %rbp
        movq    %rsp, %rbp
        leaq    .LC0(%rip), %rdi
        call    puts@PLT       # printf가 puts로 바뀜
        movl    $0, %eax
        popq    %rbp
        ret
```

- x86-64에서 `puts@plt`는 procedure linkage table(PLT) 안의 점프 대상("스텁")으로, 표준 C 라이브러리 함수 `puts()`를 호출하는 데 사용됨
- 공유 라이브러리는 프로그램 실행마다 임의의 메모리 주소에 로드되므로, 컴파일된 프로그램은 `puts()`의 정확한 주소를 미리 알 수 없음. `@plt` 스텁이 중개자 역할을 해서 실행 시점에 함수를 동적으로 찾아 점프함

**③ 어셈블** — `gcc -c hello.s -o hello.o`

- 어셈블리 → 기계어
- `hello.o` — 오브젝트 파일 (기계어, 아직 `puts` 주소를 모름)

```bash
$ objdump -d hello.o
0000000000000000 <main>:
   0:  55                     push   %rbp
   1:  48 89 e5               mov    %rsp,%rbp
   4:  48 8d 3d 00 00 00 00   lea    0x0(%rip),%rdi
   b:  e8 00 00 00 00         call   10 <main+0x10>   # ← 비어 있음
  10:  b8 00 00 00 00         mov    $0x0,%eax
  15:  5d                     pop    %rbp
  16:  c3                     ret

$ nm hello.o
0000000000000000 T main
                 U puts   # U = undefined, 링커가 채워야 함
```

- `objdump` : 컴파일된 오브젝트/실행 파일(ELF 등)의 구조를 분석하고 어셈블리어로 역어셈블 (기계어 → 어셈블리)
- `b`에는 비어 있고 `U puts` — undefined 상태로 링커가 채워야 함
- `hello.o`는 relocatable한 상태
  - `hello.o`에는 `.text`(기계어), `.data`(전역변수)가 있고 `main`만 있음, `printf` 정의는 없음
  - `hello.o` + `printf.o`(libc)를 합치는 작업이 필요 → 링크

**④ 링크** (by 링커)

- 오브젝트 + libc → 실행파일
- `hello` — 실행파일 (libc의 `puts`와 연결 완료)

```bash
$ nm hello | grep -E "main|puts"
0000000000001139 T main
                 U puts@GLIBC_2.2.5   # 동적 링크: 실행 시 libc.so에서 찾음

$ ./hello
Hello, C!
```

### 2-2. 어셈블리 읽기

```bash
cat hello.s
```

```nasm
.LC0:
        .string "Hello, C!"
main:
        pushq   %rbp
        movq    %rsp, %rbp
        leaq    .LC0(%rip), %rdi
        call    puts@PLT        # ← printf가 아니라 puts
        movl    $0, %eax
        popq    %rbp
        ret
```

- 서식(`%d`, `%s` 등)이 없고 `\n`으로 끝나는 `printf`는, 컴파일러가 더 단순한 `puts`로 바꿈 → 최적화
- `puts@plt` : 동적 링크된 프로그램에서 외부 라이브러리 함수 `puts`를 호출하기 위해 사용하는 PLT 엔트리
  - **PLT** (Procedure Linkage Table) : 외부 라이브러리 함수의 실제 주소를 찾아 연결하는 코드 테이블
  - **GOT** (Global Offset Table) : 함수의 실제 메모리 주소를 저장하는 데이터 테이블
  - 동작 과정
    1. **함수 호출** : 프로그램이 `puts`를 호출하면 `puts@plt`로 점프
    2. **초기 호출 (Runtime Resolve)** : 처음 `puts@plt`를 부를 때는 GOT에 `puts`의 실제 주소가 아직 없음. 대신 `puts@plt+6` 주소(링커로 이동하는 코드)가 들어 있어, 링커가 동적으로 `puts`의 실제 주소를 찾아 GOT에 기록

### 2-3. 오브젝트는 puts 주소를 아직 모름

```bash
nm hello.o
#                  U puts     ← U = undefined, "누군가 채워 줘야 함"
# 0000000000000000 T main     ← T = text(코드), 여기서 정의됨

nm hello | grep -E "main|puts"
# 0000000000001139 T main
#                  U puts@GLIBC_2.2.5   ← 링크 후: 실행 시 libc.so에서 찾기로 연결됨
```

- `nm` : 바이너리 파일에 포함된 심볼(함수, 변수 이름) 정보 확인
- `puts` : `stdio.h`의 문자열 출력 함수 `puts` 참조 기호
- **U = undefined**, 해당 오브젝트 파일 내 함수가 선언만 되어 있고 실제 구현(기계어 코드)은 포함되어 있지 않음
  - `puts`는 화면에 문자열을 출력하는 공용 함수
  - `.c`를 컴파일해 `.o`를 만들 때, 컴파일러는 `puts`가 존재한다는 것만 알고 자리를 임시로 비워둠
  - 링커가 최종 실행 파일을 만드는 과정에서 표준 라이브러리(libc)와 연결되면 `U` 상태가 해제되고 실제 메모리 주소가 할당됨

### 2-4. 함정 — 링크 에러

```c
// link_err.c
#include <stdio.h>
int read_sensor(void);   // 선언만 있고 정의(본문)가 없다

int main(void) {
    printf("%d\n", read_sensor());
    return 0;
}
```

```bash
gcc -c link_err.c               # ③ 어셈블까지는 성공! (선언이 있으니 컴파일러는 만족)
gcc link_err.o -o link_err      # ④ 링크에서 실패
# → undefined reference to `read_sensor'
```

정상적인 흐름과 비교:

```bash
gcc -E hello.c -o hello.i     # ① 전처리
gcc -S hello.i -o hello.s     # ② 컴파일
gcc -c hello.s -o hello.o     # ③ 어셈블
gcc hello.o -o hello          # ④ 링크
ls hello*                     # hello  hello.c  hello.i  hello.o  hello.s
```

- `read_sensor`는 선언만 하고 **정의는 하지 않음** → 어셈블까지는 가능
- 링크 단계에서 정의를 찾으려 했으나 어느 `.o`에서도 찾지 못함 → `undefined reference`
- 흔한 원인: 함수 이름 오타, `.c` 파일 누락, 라이브러리 옵션(`-lm` 등) 누락

### 2-5. 최적화 수준 비교

```bash
gcc -S -O0 hello.c -o o0.s
gcc -S -O2 hello.c -o o2.s
wc -l o0.s o2.s     # -O2가 더 짧다
diff o0.s o2.s      # pushq %rbp / movq %rsp,%rbp가 사라진 것을 확인
```

- `-O0` : 디버깅하기 쉽게 코드를 그대로 유지
- `-O2` : 프레임 포인터 생략 등으로 코드를 줄임
- 불필요한 프레임 설정·저장 명령을 최적화로 없애서 `-O2`가 더 짧음
- 임베디드 릴리스 빌드에는 `-O2`, 크기를 우선할 때는 `-Os`

## 3. 헤더/소스 분리와 Makefile

### 3-1. 파일 3개로 나누기

```c
// sensor.h
#ifndef SENSOR_H
#define SENSOR_H

typedef struct {
    double t;   // 온도
    int    h;   // 습도
    int    d;   // 거리(mm)
} Reading;

int  is_alert(Reading r);
void print_reading(Reading r);   // 구현 코드 없이 무슨 함수가 있는지 알림

#endif
```

- **헤더 파일(.h)** — 함수 프로토타입, 매크로 정의, 자료형, 여러 소스 파일이 공유하는 상수를 선언
  - 실제 코드 없이 컴파일러에게 "이런 함수·변수가 있다"는 것만 알림
- 왜 사용하는가?
  - 코드 재사용성
  - 관심사 분리 : 인터페이스(무엇을 하는가) ↔ 구현(어떻게 하는가)를 분리
  - 빠른 컴파일
- 종류
  - 표준 라이브러리 : `<>` — 예) `<stdio.h>`, `<stdlib.h>`
  - 사용자 정의 : `" "`
- **항상 include guard(`#ifndef`, `#define`, `#endif`)를 사용**
  - 컴파일러가 같은 헤더 파일을 실수로 두 번 처리해 빌드 에러가 나는 것을 방지

```c
// sensor.c
#include <stdio.h>
#include "sensor.h"   // 헤더 파일 include

int is_alert(Reading r) {
    return r.t > 35.0;
}

void print_reading(Reading r) {
    printf("T=%.1f H=%d D=%d %s\n", r.t, r.h, r.d, is_alert(r) ? "ALERT" : "OK");
}
```

- **소스 파일** — 정의. 헤더 파일에서 선언한 함수들을 정의

```c
// main.c
#include "sensor.h"

int main(void) {
    Reading r1 = {25.3, 60, 120};
    Reading r2 = {36.9, 70, 150};
    print_reading(r1);   // → T=25.3 H=60 D=120 OK
    print_reading(r2);   // → T=36.9 H=70 D=150 ALERT
    return 0;
}
```

- 메인 프로그램. 메인에서 함수들을 호출 가능

```bash
gcc -Wall -Wextra main.c sensor.c -o app && ./app
```

- `"sensor.h"` : 사용자 정의 헤더 파일 → 현재 폴더에서 먼저 찾음
- `<stdio.h>` : 시스템 라이브러리 헤더 파일 → 시스템 경로만 찾음

### 3-2. 함정 — 헤더 가드 지우기

```c
// sensor.h — 헤더 가드를 지운 버전
typedef struct {
    double t;
    int    h;
    int    d;
} Reading;

int  is_alert(Reading r);
void print_reading(Reading r);
```

```c
// main.c — 헤더 파일을 두 번 include
#include "sensor.h"
#include "sensor.h"

int main(void) {
    Reading r1 = {25.3, 60, 120};
    Reading r2 = {36.9, 70, 150};
    print_reading(r1);
    print_reading(r2);
    return 0;
}
```

```bash
gcc -Wall -Wextra main.c sensor.c -o app
# → error: redefinition of 'struct <anonymous>'
# → error: conflicting types for 'Reading'
```

- 함수 선언은 여러 번 나와도 괜찮음
- **구조체·typedef 정의는 한 번만 허용** → 구조체 정의가 두 번 나오면 `redefinition` 에러

### 3-3. Makefile

```makefile
CC     = gcc
CFLAGS = -Wall -Wextra -O2

# default
app: main.o sensor.o
	$(CC) $(CFLAGS) -o app main.o sensor.o

main.o: main.c sensor.h
	$(CC) $(CFLAGS) -c main.c

sensor.o: sensor.c sensor.h
	$(CC) $(CFLAGS) -c sensor.c

# 파일 정리 규칙
clean:
	rm -f *.o app
```

```bash
make            # 세 줄의 gcc가 실행됨
make            # → make: 'app' is up to date.   (아무것도 안 함)
touch sensor.c  # sensor.c만 "수정"
make            # sensor.o와 app만 다시 만들어짐
touch sensor.h  # 헤더 수정
make            # main.o, sensor.o, app 전부 — 둘 다 sensor.h에 의존하므로
make clean      # 산출물 삭제
```

**Makefile** — 프로그램 빌드와 컴파일 과정을 자동화하기 위해 작성하는 설정 파일

- **Target** : 결과물
- **Prerequisites** : 타겟을 만들기 위해 필요한 원본 파일·다른 파일 목록
- **Recipe** : 실제 실행 명령어. 반드시 탭(tab) 필요
- `CC` : 매크로 변수, `CFLAGS` : 플래그 설정

동작 방식:

- `make` → default target을 찾아서 `app`을 만들려고 시도 → 최종 타겟이 `app`이면 `main.o`와 `sensor.o`가 필요 ⇒ 의존성 검사
- `main.o: main.c sensor.h`
  - **처음 실행할 때** : `main.o` 파일이 없음 → `gcc -c main.c` 실행해 파일을 만듦
  - **다시 실행할 때 (수정 시간이 같을 때)** : `main.o`가 이미 있고 `main.c`, `sensor.h`가 그 이후로 수정된 적이 없다면 컴파일을 건너뜀 (`up to date`)
  - **헤더를 고쳤을 때 (`touch sensor.h`)** : `sensor.h`의 수정 시간이 결과물인 `main.o`보다 최신 → 재컴파일
- `sensor.o`도 마찬가지
- 파일 점검이 끝나면 `app`으로 돌아와 링킹

> Target : 의존 파일이 타깃보다 새로우면 명령을 실행한다. 헤더를 의존성에 적지 않으면 헤더를 고쳐도 `.o`가 바뀌지 않아 그대로 링크되어 변경이 반영되지 않는다.


## 4. 자료형, 메모리 표현

### 4-1. sizeof

```c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    printf("char     %zu\n", sizeof(char));
    printf("short    %zu\n", sizeof(short));
    printf("int      %zu\n", sizeof(int));
    printf("long     %zu\n", sizeof(long));
    printf("float    %zu\n", sizeof(float));
    printf("double   %zu\n", sizeof(double));
    printf("uint8_t  %zu\n", sizeof(uint8_t));
    printf("int32_t  %zu\n", sizeof(int32_t));
    printf("int *    %zu\n", sizeof(int *));
    return 0;
}
```

결과 (x86-64 Linux):

| 타입 | 크기(byte) |
|---|---|
| char | 1 |
| short | 2 |
| int | 4 |
| **long** | **8** |
| float | 4 |
| double | 8 |
| **uint8_t** | **1** |
| **int32_t** | **4** |
| **int \*** | **8** |

- `long`은 Windows에서 4바이트, `int *`는 32bit MCU에서 4바이트
- 플랫폼마다 사이즈가 다르기 때문에 임베디드에서는 `stdint.h`의 고정폭 타입(`uint8_t`, `int32_t` 등)을 사용
- `%zu` : `size_t` 출력용 서식
  - `z` — 크기를 자동으로 결정
  - `size_t` : C/C++에서 객체·메모리 크기, 배열 인덱스를 나타내기 위해 사용하는 부호 없는 정수(unsigned integer) 타입
- `int8_t` : -128 ~ 127, `uint8_t` : 0 ~ 255 (unsigned)

### 4-2. Little Endian

```c
#include <stdio.h>

int main(void) {
    int v = 0x11223344;
    unsigned char *p = (unsigned char *)&v;   // v의 첫 바이트 주소
    printf("%02X %02X %02X %02X\n", p[0], p[1], p[2], p[3]);
    return 0;
}
```

```text
44 33 22 11
```

- **Little Endian** : 최하위 바이트("little end")를 가장 낮은 메모리 주소에 저장 — 낮은 주소에 낮은 바이트
- `(unsigned char *)&v` : `int`형 변수의 주소를 1바이트씩 쪼개서 읽겠다는 의미
  1. `&v`로 주소를 생성하면 컴파일러는 이를 `int *`(4바이트 단위 주소)로 인식 → 시작 주소를 `0x1000`이라 가정하면, 4바이트 전체를 읽어 하나의 숫자 `0x11223344`로 처리
  2. `(unsigned char *)`로 포인터를 형변환하면 시작 주소는 `0x1000`으로 같지만, 데이터를 읽는 단위가 1바이트로 축소됨 → `p[0]`은 `p+0` 번지 값 `44`, `p[1]`은 `p+1` 번지 값 `33`
- 주의: 네트워크 바이트 순서는 빅 엔디안(반대)이므로 통신 프로토콜에서는 반드시 확인 필요

### 4-3. 함정 — 오버플로

```c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    uint8_t a = 250;
    a += 10;                 // 260은 8비트로 표현 불가
    int8_t b = 127;
    b++;                      // 01111111 + 1
    int x = 300;
    unsigned char c = x;      // 0x12C에서 하위 1바이트만
    printf("%d %d %d\n", a, b, c);
    return 0;
}
```

```text
4 -128 44
```

- `a` : 260, 8비트는 256까지 → 260 - 256 = 4로 **감김(wrap-around)**
- `b` : 128 = `0b10000000` → 최상위 비트가 1이 되어 **음수**로 해석됨, 결과 -128
- `c` : 300 = `0x12C`이고 `char`는 1바이트만 읽으므로 `c` = `0x2C` = 44

### 4-4. 같은 비트, 다른 해석

```c
#include <stdio.h>

int main(void) {
    unsigned char u = 200;
    signed char   s = u;        // 같은 비트 11001000
    printf("%u %d\n", u, s);    // → 200 -56
    printf("%d\n", 200 - 256);  // → -56  (2의 보수: 값 − 2^8)
    return 0;
}
```

```text
200 -56
-56
```

- `u`는 `unsigned char`, 비트 패턴 `0b11001000`, 값 200
- `s`에 `u`를 대입하지만 `s`는 `signed`이므로 같은 비트가 -56으로 해석됨
- `200 - 256`도 결과적으로 같은 -56 (2의 보수 표현)

## 5. 형변환, 오버플로, 실수 정밀도

### 5-1. 함정 — `-1 < 1` ?

```c
#include <stdio.h>

int main(void) {
    printf("%d\n", -1 < 1);              // → 1  (참)
    printf("%d\n", -1 < 1u);             // → 0  (거짓!)
    printf("%d\n", -1 < sizeof(int));    // → 0  (거짓!)
    printf("%u\n", (unsigned)-1);        // → 4294967295
    return 0;
}
```

```text
gcc -Wall -Wextra promo.c -o promo
# warning: comparison of integer expressions of different signedness [-Wsign-compare]
```

- `-1 < 1` : 둘 다 `int`이므로 그대로 비교
- `-1 < 1u` : `1u`는 `unsigned int`. `int`가 `unsigned`로 변환되어 비교됨 → `-1`은 `0xFFFFFFFF`, 즉 `unsigned`로는 4294967295가 되므로 거짓
- `-1 < sizeof(int)` : `sizeof(int)`의 타입은 `size_t`(=`unsigned long`)
  - `-1`이 `unsigned long`으로 변환되어 18446744073709551615이 되므로 거짓
  - `-Wextra`가 이런 부호 관련 오류를 잡아줌
- `(unsigned)-1`도 마찬가지로 4294967295

### 5-2. 정수 승격

```c
#include <stdio.h>

int main(void) {
    char c = 'A';
    printf("%zu %zu\n", sizeof(c), sizeof(c + 1));   // → 1 4
    printf("%c %d\n", c + 1, c + 1);                 // → B 66
    return 0;
}
```

1. `sizeof(c)` : `c`는 `char`이므로 1
2. `sizeof(c + 1)` : `int`보다 작은 타입은 연산에 들어가는 순간 `int`로 승격되므로 4
3. `%c`, `c + 1` : `%c`는 `char`로 출력하므로 'A'의 다음 문자 'B' 출력
4. `%d`, `c + 1` : `%d`는 `int`로 출력하므로 'A'의 아스키코드 65에 1을 더한 값 66 출력

### 5-3. 함정 — 정수 나눗셈

```c
#include <stdio.h>

int main(void) {
    printf("%d\n",   7 / 2);        // → 3     (정수 나눗셈, 버림)
    printf("%.1f\n", 7 / 2.0);      // → 3.5   (한쪽만 실수여도 실수 연산)
    printf("%d\n",   7 % 2);        // → 1     (나머지)

    int c = 26;
    double f1 = c * 9 / 5 + 32;     // 왼쪽부터: 234 / 5 = 46 (이미 잘림)
    double f2 = c * 9.0 / 5 + 32;
    printf("%.1f %.1f\n", f1, f2);  // → 78.0 78.8
    return 0;
}
```

1. `7 / 2` : 정수끼리의 나눗셈은 정수 연산, 소수점 버림
2. `7 / 2.0` : 정수 / 실수 나눗셈은 실수 연산이 됨
3. `7 % 2` : 나머지 연산
4. `f1` : 모든 항이 정수이므로 계산 중 소수점이 잘려 결과가 78
5. `f2` : 실수 9.0이 포함되어 있어 78.8
6. `printf`에서 `%.1f`로 출력하면 각각 78.0, 78.8

### 5-4. 실수 비교

```c
#include <stdio.h>
#include <math.h>

int main(void) {
    double a = 0.1 + 0.2;
    printf("%d\n", a == 0.3);                 // → 0
    printf("%.20f\n", a);                     // → 0.30000000000000004441
    printf("%d\n", fabs(a - 0.3) < 1e-9);     // → 1  (오차 범위 비교)
    printf("%d\n", (int)3.99);                // → 3  (캐스팅은 버림, 반올림 아님)
    return 0;
}
```

```bash
gcc -Wall -Wextra fp.c -o fp -lm     # math.h를 쓰면 -lm으로 링커에 libm을 알림
```

1. IEEE 754 표준에서 0.1, 0.2는 십진수처럼 딱 떨어지지 않는 무한소수가 되어 미세한 오차가 발생함
2. `a == 0.3` : `0.1 + 0.2`를 계산하면 `0.30000000000000004441…`이 되고, `0.3`은 `0.29999999999999998890…`으로 서로 다른 비트로 저장되어 있어 결과는 거짓(0)
3. `%.20f`로 `a`를 출력하면 정확히 0.3이 아니라 오차가 있음을 확인할 수 있음
4. `fabs(a - 0.3) < 1e-9` : 실수 비교 시 `==` 대신, 두 값 차이의 절댓값이 매우 작은 값(epsilon, `10^-9`)보다 작은지 확인
   - `fabs` : `<math.h>`(C++에서는 `<cmath>`)의 `double`형 절댓값 반환 함수
5. `(int)3.99` : 캐스팅은 실수형을 정수형으로 강제 변환하며, 소수점 아래는 무조건 버림 (반올림 아님)

> `math.h`를 사용할 때는 `-lm` 옵션을 붙여 수학 라이브러리(`libm.a`)를 명시적으로 링크해야 함. `-lm` 없이 컴파일하면 `undefined reference to 'fabs'`라는 링크 단계 에러가 발생한다.

## 6. 연산자와 제어문

### 6-1. 함정

```c
#include <stdio.h>

int main(void) {
    int x = 0;
    if (x = 5) printf("A\n");            // → A   (대입! 항상 참)
    if (x == 5) printf("B\n");           // → B

    int a = 2, b = 4;
    printf("%d %d\n", a & b, a && b);    // → 0 1  (비트 AND vs 논리 AND)

    printf("%d\n", 1 << 3 + 1);          // → 16  (+가 먼저: 1 << 4)
    printf("%d\n", (1 << 3) + 1);        // → 9
    return 0;
}
```

```text
warning: suggest parentheses around assignment used as truth value
warning: suggest parentheses around '+' inside '<<'
```

1. `if (x = 5)` : `x`에 5를 대입하는 문장이라 항상 참 → 'A' 출력 (논리적 오류, logical error)
2. `if (x == 5)` : `x`가 5인지 비교 → 'B' 출력
3. `a & b`, `a && b`
   - `a & b` (비트 AND) : `0010 & 0100 = 0000` → 0. 비트 연산자는 이진수 각 비트 단위로 연산해 정수 값을 반환
   - `a && b` (논리 AND) : `a`, `b` 모두 0이 아니므로 둘 다 참 → `참 && 참` = 참 → 1. 논리 연산자는 참/거짓 조건을 판별해 불리언 값을 반환
4. `1 << 3 + 1` : `+`가 먼저 계산되어 `1 << 4` → 1을 왼쪽으로 4번 시프트, `00001` → `10000` = 16
5. `(1 << 3) + 1` : 1을 3번 왼쪽으로 시프트한 값에 1을 더함, `0b1000 + 1 = 0b1001` = 9

### 6-2. switch

```c
#include <stdio.h>

int main(void) {
    int level = 2;
    switch (level) {
        case 1:  printf("FREEZE ");
        case 2:  printf("COLD ");           // break 없음
        case 3:  printf("NORMAL "); break;
        case 4:  printf("WARM ");
        default: printf("ALERT ");
    }
    printf("\n");   // → COLD NORMAL
    return 0;
}
```

```text
warning: this statement may fall through [-Wimplicit-fallthrough=]
```

`level`이 2이므로 `case 2`의 "COLD"가 출력됨 → `break`가 없으므로 `case 3`의 "NORMAL"까지 이어서 출력 → `break`문을 만나 switch문을 탈출

**Fall-through** : `break`문이 없을 때, 일치하는 `case` 실행 후 멈추지 않고 다음 `case` 코드까지 이어서 실행되는 현상. `-Wextra`는 fall-through도 잡아내므로, 의도적인 fall-through는 주석을 달아 경고를 없앤다.

```c
case 'y': case 'Y':     // 값이 여럿, 처리는 하나 — 빈 case는 경고 없음
    ok = 1; break;
case 1:
    prepare();
    // fall through      ← 의도 표시
case 2:
    run(); break;
```

### 6-3. 온도 판정

```c
#include <stdio.h>

const char *level(double t) {
    if (t < 0)       return "FREEZE";
    else if (t < 20) return "COLD";
    else if (t < 30) return "NORMAL";
    else if (t < 40) return "WARM";
    return "ALERT";
}

int main(void) {
    double temps[] = {-5, 25, 45};
    for (int i = 0; i < 3; i++)
        printf("%.0f → %s\n", temps[i], level(temps[i]));
    return 0;
}
```

```text
-5 → FREEZE
25 → NORMAL
45 → ALERT
```

`const char *` : 포인터가 가리키는 데이터 값은 바꿀 수 없지만, 포인터 변수 자신이 가리키는 주소는 다른 곳으로 바꿀 수 있는, 상수 데이터를 가리키는 포인터. 문자열 리터럴을 가리키는 포인터로 흔히 사용된다.

### 6-4. 반복문 — 소수 판별

```c
#include <stdio.h>

int is_prime(int n) {
    if (n < 2) return 0;
    for (int i = 2; i * i <= n; i++)      // √n까지만 검사
        if (n % i == 0) return 0;
    return 1;
}

int main(void) {
    int count = 0;
    for (int n = 2; n <= 100; n++) {
        if (!is_prime(n)) continue;       // 소수가 아니면 다음 n으로
        printf("%3d ", n);
        if (++count % 10 == 0) printf("\n");
    }
    printf("\n");
    return 0;
}
```

## 7. 함수와 스코프

### 7-1. 값 전달 (call by value)

```c
#include <stdio.h>

void inc(int x) {
    x++;                          // 복사본 x
    printf("안: %d\n", x);
}

int main(void) {
    int a = 5;
    inc(a);                       // → 안: 6
    printf("밖: %d\n", a);        // → 밖: 5
    return 0;
}
```

```text
안: 6
밖: 5
```

1. `main`에서 `int a = 5;` 정의
2. `inc(a)`로 `a`의 값을 함수로 전달. `x`가 5이므로 `x++`으로 증가시켜 "안: 6" 출력
3. 하지만 `a`는 함수로 값만 전달될 뿐, 함수 안의 변경이 함수 밖에는 영향을 주지 못함
4. 그래서 바깥의 `printf`에서 `a`는 여전히 5

⇒ 원본을 바꾸려면 주소를 넘겨야 함 — 포인터 사용

### 7-2. 재귀, 스택 vs 데이터 영역

```c
#include <stdio.h>

static int calls = 0;             // 데이터 영역: 프로그램 끝까지 산다

int fact(int n) {
    calls++;
    printf("%*sfact(%d) 진입\n", (3 - n) * 2, "", n);   // 들여쓰기로 깊이 표시
    if (n <= 1) return 1;
    int r = n * fact(n - 1);      // 재귀
    printf("%*sfact(%d) → %d\n", (3 - n) * 2, "", n, r);
    return r;
}

int main(void) {
    int r = fact(3);              // 먼저 변수에 받는다 — 이유는 예제 7-4에서
    printf("결과 %d, 호출 %d번\n", r, calls);
    return 0;
}
```

```text
fact(3) 진입
  fact(2) 진입
    fact(1) 진입
  fact(2) → 2
fact(3) → 6
결과 6, 호출 3번
```

- `%*s` : 출력할 문자열의 최소 너비를 인자 값으로 직접 전달받아 우측 정렬
- `fact(3)` 호출 흐름
  - `calls` 1, `fact(3)` 진입
  - `r = 3 * fact(2)`
    - `fact(2)`, `calls` 2, `fact(2)` 진입
    - `r = 2 * fact(1)`
      - `fact(1)`, `calls` 3, `fact(1)` 진입, `return 1`
    - `r = 2`, `fact(2) → 2`
  - `r = 6`, `fact(3) → 6`
- 결과: 6, 호출 3번 → 스택에 LIFO로 저장됨
- `calls`는 함수 밖에 `static`으로 선언되어 정적 전역 변수가 되었고, 프로그램이 살아 있는 동안 계속 데이터 영역에 저장됨 (static global variable)

### 7-3. 함수 안의 static

```c
#include <stdio.h>

int next_id(void) {
    static int id = 0;            // 첫 호출에 한 번만 초기화
    return ++id;
}

int main(void) {
    printf("%d\n", next_id());    // → 1
    printf("%d\n", next_id());    // → 2
    printf("%d\n", next_id());    // → 3
    return 0;
}
```

**Local static variable** (함수 안의 static 변수, block scope)

- 데이터 영역에 저장되어 여러 번 함수를 호출해도 값을 유지함
  - 보통의 지역 변수는 스택에 있다가 함수가 끝나면 사라짐
- 프로그램 실행 동안 계속 존재
- 함수에 대해 local함 → 함수 밖에서 접근 불가 ⇒ no linkage
- 초기화는 함수가 처음 호출될 때 한 번만 수행됨
- 함수 안에서만 visible

**Global static variable** (함수 밖의 static 변수, file scope)

- 데이터 영역에 저장되어 프로그램 실행 동안 존재
- 같은 C 파일에 있는 어느 함수에게도 visible
- internal linkage로 다른 파일에서는 접근 불가능

### 7-4. 함정 — 인자 평가 순서는 정해져 있지 않음

```c
#include <stdio.h>

int next_id(void) { static int id = 0; return ++id; }

int main(void) {
    printf("%d %d %d\n", next_id(), next_id(), next_id());   // → 3 2 1  (gcc)
    return 0;
}
```

함수의 인자 평가 순서(function's argument evaluation order)는 **unspecified behaviour**다.

gcc는 인자를 오른쪽에서 왼쪽으로 평가한다.

```
printf("%d %d %d\n", next_id(), next_id(), next_id());
```

- 맨 오른쪽의 `next_id()` → `id = 1`
- 중간 `next_id()` → `id = 2`
- 맨 왼쪽 `next_id()` → `id = 3`

⇒ 출력 결과: `3 2 1`

⇒ 부수효과(side effect)가 있는 호출을 한 식에 여러 번 넣지 말 것. 순서가 중요하면 변수에 대입해서 호출한다.

```c
int a = next_id(); // 1
int b = next_id(); // 2
int c = next_id(); // 3

printf("%d %d %d\n", a, b, c);
```

> C 함수 호출 규약(cdecl 표준, C declaration)에서는 함수 인자를 뒤에서부터 전달한다.

### 7-5. 재귀의 한계

```c
#include <stdio.h>

int depth(int n) { return n == 0 ? 0 : 1 + depth(n - 1); }

int main(void) {
    printf("%d\n", depth(10000));       // 보통 OK
    printf("%d\n", depth(10000000));    // → Segmentation fault (스택 오버플로)
    return 0;
}
```

- `depth()`는 `n`만큼 1을 더해가며 재귀 호출하는 함수
- `depth(10000)`은 정상적으로 10000을 출력하지만
- `depth(10000000)`은 스택 오버플로가 일어나 세그멘테이션 폴트가 발생함
- PC의 스택은 보통 8MB, ESP32의 task stack은 수 KB 수준이므로, 임베디드에서 재귀는 깊이를 확실히 알 때만 사용해야 한다
